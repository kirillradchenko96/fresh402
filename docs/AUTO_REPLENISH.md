# Customer-controlled replenishment

Production 3.0.1 uses the Safe merchant and offers all-service purchasing under the live flags and accepted package terms. This optional reference client has no automatic execution or signing enabled by publication. Its owner must explicitly select a package, pin the current merchant policy and approve a bounded spending policy. Existing packages and original-operation recovery retain their original terms.

The optional [Node.js 24 reference client](../examples/knowledge-base/auto-replenish.ts) performs one bounded pass when the customer invokes `tick()`. Fresh402 cannot charge a wallet arbitrarily. There is no subscription, unlimited approval, background timer or payment on import. Live feature flags and exact quotes remain authoritative. This integration does not authorize the Fresh402 owner's funds.

The customer explicitly pins a trusted API origin, EOA payer, Base 8453, native USDC, known merchant recipient, allowed and selected package IDs, accepted all-service terms where applicable, credit threshold, per-purchase/day/month atomic-USDC ceilings and maximum lifetime purchase count. The client rejects price/credit/recipient/chain/asset changes before signing. Current package amounts are 2,500,000 or 15,000,000 atomic USDC (six decimals), for 1,000 or 10,000 credits.

Keep one private SQLite file for the entire owner budget, outside every Git worktree. Secure it and its WAL/SHM files with owner-only OS permissions and encrypted storage. Its immutable policy and conservative budget reservations survive restarts. Parallel processes share a single outstanding purchase and a transaction/lease lock. Do not copy/reset the database or use multiple databases to bypass the budget; these are cooperative client controls, not a blockchain-enforced allowance. A delegated wallet signer must independently enforce the owner's policy and emergency stop. Never supply a private key or seed phrase to the merchant.

Supply an `AuthorizationVault` backed by the customer's encrypted private store or wallet custody system. `authorizeAndPersist` must save the original exact payment payload durably before returning. `load` recovers that same payload. The SQLite file stores intent, quote, phase and proof hash, never the signature, seed, private key or API key. Signing is requested once after persisting a marker; a crash or uncertain signature holds further purchases rather than requesting a replacement signature.

Each reservation pins one purchase idempotency key, original intent, nonce, package, exact amount, accepted terms and recipient. EIP-3009 validity is bounded by both the original five-minute quote and its reserved UTC day; `validAfter` excludes earlier days and `validBefore` excludes the next day/month. Failed/expired reservations still consume policy budget conservatively. All-service packages require canonical finalized settlement; early credits are not replenishment success.

After an uncertain submission, later passes only read the original status. No second submission or replacement signature is sent. An unsubmitted expired authorization can be released only after the server's authenticated read-only finalized-unused inspection. Submitted/settling payments remain held for server recovery. A terminal genuine finalized credit confirms success; local fixture receipts are not evidence of mainnet acceptance. Missing proof requires the customer's own secure-store recovery; the client fails closed.

`disable()` is persistent and prevents subsequent signing/submission steps. Already submitted authorizations remain recoverable through the separate read-only customer client. An already signed authorization cannot be revoked by stopping this JavaScript library; retain its exact evidence and observe expiry/finality. A long-running wallet interaction that loses its lease cannot initiate submission. There is no automatic credential rotation after a top-up.

For new all-service packages, inspect `/v3/prepaid/all-services` and explicitly accept `terms_digest`; new canonical IDs are `starter-all-services-v4` and `developer-all-services-v4`. Only finalized credits from those purchases acquire the new blockchain eligibility. Legacy packages and balances retain their original rights, prices and nonexpiration; eligible credits are a provenance subset, never a duplicate grant. Costs are Check 2, Extract 3, Smart Diff 4, OpenAPI Diff 5, Contract Watch 4, Wallet Watch 8 and Token Facts 4. Finite admission/provider limits remain. Do not infer enablement from the existence of this guide: use the live `enabled` flag and package catalog.
